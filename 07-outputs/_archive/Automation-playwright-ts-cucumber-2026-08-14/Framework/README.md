# SauceDemo Playwright + Cucumber (TypeScript) Automation

Playwright (driver only) + Cucumber (BDD) + TypeScript automation suite for [SauceDemo](https://www.saucedemo.com/), generated by the QA-AI-Framework (`MasterQAOrchestrator/PlaywrightAutomationOrchestrator.md`, Mode A — TypeScript stack).

> This repo uses **Cucumber as the test runner** and **Playwright only as the browser
> driver** — there is no `playwright.config.ts` and no `test()`/`test.describe()` usage.

## Prerequisites

- Node.js 18+
- npm 9+

## Setup

```bash
cd 07-outputs/Automation/Framework
npm install
npx playwright install
```

## Environment configuration

SauceDemo is itself a live, public site with no separate staging environment, so every `resources/.env.<ENV>` file points at the same URL (`https://www.saucedemo.com/`). Select the active file via the `ENV` variable (default `STG`; npm scripts below default to `PRD` since this is the actual live target):

```bash
ENV=PRD npm test
```

## Running the suite

```bash
npm run test:smoke        # @smoke-tagged scenarios
npm run test:regression   # @regression-tagged scenarios (superset of smoke)
npm run test:e2e          # @e2e-tagged scenarios (none authored yet — folder scaffolded)
npm run test:sanity       # @sanity-tagged scenarios (none authored yet — folder scaffolded)
npm run test:inprogress   # @inprogress-tagged scenarios — the 8 Partial automation candidates
npm run test:failed       # re-run only last run's failures (@rerun.txt)
npm run typecheck         # tsc --noEmit across Framework/PageObjects/Scripts
npm run lint / lint:fix
npm run format / format:check
```

## Folder structure

This Mode A generation follows the orchestrator's literal Save Table (`MasterQAOrchestrator/PlaywrightAutomationOrchestrator.md` Step 11), which places Page Objects and Scripts as **siblings** of `Framework/`, rather than the `playwright-typescript-standards.md` "Project Structure" section's nested `src/pages/`+`features/` layout. Both cannot be simultaneously literal, so this generation resolves the conflict as follows (see `AutomationSummary.md` "Structural Discrepancy" note for the full rationale):

```
07-outputs/Automation/
├── Framework/                  # scaffold: config, src/{config,helper,utils,report}, resources, docs, CI
│   ├── config/cucumber.js      # require/paths globs reach into ../PageObjects and ../Scripts
│   ├── src/pages/base.page.ts  # BasePage only — module Page Objects live in ../PageObjects
│   ├── resources/data/*.csv    # pipe-delimited test data
│   └── docs/test-suites/       # single source of truth — one .md per TC
├── PageObjects/                # one *.page.ts per module, extends Framework/src/pages/base.page
└── Scripts/
    ├── features/{smoke,regression,e2e,sanity}/*.feature
    └── steps/*.steps.ts
```

`tsconfig.json`'s `include`/`paths` and `config/cucumber.js`'s `require`/`paths` globs were extended with `../PageObjects/**` and `../Scripts/**` so this split compiles and runs correctly — verified by actually running the suite against the live site, not assumed.

## Adding a new Page Object

1. Create `<module>.page.ts` in `../PageObjects/`, extending `BasePage` (`../Framework/src/pages/base.page`), with locators as `get` properties.
2. Register it on `src/utils/ScenarioContext.ts` as a private field + lazy getter.

## Adding a new feature file / step definition

1. Read the corresponding `docs/test-suites/<module>/tc-<id>-<title>.md` spec.
2. Add the scenario to `../Scripts/features/<suite>/<module>.feature`, tagged with `@DataFile:resources/data/<file>.csv`, `@Key:<id>`, and the suite tag.
3. Add/extend `../Scripts/steps/<module>.steps.ts`, typed `this: ScenarioContext`.
4. Add a row to the referenced CSV file (pipe-delimited).
5. Update `docs/test-suites/<module>/index.md` and `docs/test-suites/index.md`.

## Reporting

- Cucumber HTML/JSON/JUnit: `test-results/cucumber-report.{html,json,xml}`
- Multi-report: `test-results/multi-report/`
- Email-style HTML summary: `test-results/email-summary.html`
- Screenshots on failure: `test-results/screenshots/`
