# Selenium Java Standards

## Objective

Define the framework structure, coding conventions, and quality bar for all **Selenium WebDriver + Java + TestNG + Maven** automation generated by the QA-AI-Framework.

This is the **only** Selenium stack supported by this framework — plain Java, Page Object Model, TestNG for test verification/orchestration, and the latest stable Selenium WebDriver (Selenium 4.x, W3C WebDriver protocol). There is no Cucumber/BDD layer, no Kotlin/Groovy test code, and no JUnit variant — TestNG is mandatory for suite structure, groups, listeners, and assertions.

---

## Technology Stack

| Concern | Choice |
|---|---|
| Language | Java 17 (LTS) |
| Build Tool | Maven |
| Browser Driver | Selenium WebDriver 4.x (latest stable — W3C protocol, relative locators, `DevTools`, `SearchContext`) |
| Driver Binary Management | WebDriverManager (`io.github.bonigarcia:webdrivermanager`) — never manually download/commit driver binaries |
| Test Runner / Assertions | TestNG (`@Test`, `@BeforeMethod`/`@AfterMethod`, `@BeforeSuite`/`@AfterSuite`, groups, `Assert`/`SoftAssert`, `@DataProvider`) |
| Design Pattern | Page Object Model (POM) — `PageFactory.initElements()` + `@FindBy` |
| Explicit Waits | `WebDriverWait` + `ExpectedConditions` (or Selenium 4 `FluentWait`) — **never** `Thread.sleep()` |
| Config | Owner library (`@Config.Sources`) or plain `Properties`, environment-scoped `config-<env>.properties` |
| Reporting | ExtentReports (`ExtentSparkReporter`) |
| Logging | Log4j2 |
| Test Data | CSV (comma-delimited, header row + `Key` column) via Apache Commons CSV or OpenCSV, or JSON via Jackson |
| Data Generation | JavaFaker (optional, for synthetic data) |
| CI | Jenkinsfile (parameterized by `ENV`) and/or GitHub Actions workflow |

## `pom.xml` Standards

Required dependencies (use the latest stable version of each at generation time — do not pin to a specific historical version unless the user's existing project already pins one):

- `org.seleniumhq.selenium:selenium-java` — latest 4.x
- `io.github.bonigarcia:webdrivermanager` — automatic driver binary resolution
- `org.testng:testng`
- `com.aventstack:extentreports`
- `org.apache.logging.log4j:log4j-core` + `log4j-api`
- `org.aeonbits.owner:owner` (config) — or plain `java.util.Properties` if the target project already uses that
- `org.projectlombok:lombok`
- `com.fasterxml.jackson.core:jackson-databind` (JSON test data)
- `org.apache.commons:commons-csv` or `com.opencsv:opencsv` (CSV test data)
- `com.github.javafaker:javafaker` (optional synthetic data)

Wire `maven-surefire-plugin` to run via the TestNG suite XML:

```xml
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-surefire-plugin</artifactId>
  <configuration>
    <suiteXmlFiles>
      <suiteXmlFile>config/testng_config.xml</suiteXmlFile>
    </suiteXmlFiles>
  </configuration>
</plugin>
```

Never manually download or commit `chromedriver`/`geckodriver`/`msedgedriver` binaries — WebDriverManager resolves them at runtime (`WebDriverManager.chromedriver().setup();`).

## Base Classes

### `BaseTest.java`

- `@BeforeMethod` — resolves the browser from config/system property, calls `DriverFactory.initDriver(browser)`, maximizes window, sets implicit-free explicit-wait strategy
- `@AfterMethod` — captures a screenshot on failure (`ITestResult.FAILURE`) via `ScreenshotUtils`, then `DriverManager.quitDriver()`
- Exposes `protected WebDriver driver` via `DriverManager.getDriver()` (ThreadLocal-backed, for safe parallel execution)
- Never expose a static, non-ThreadLocal `WebDriver` field — parallel TestNG execution requires thread-safety

### `BasePage.java`

- Constructor `public BasePage(WebDriver driver) { this.driver = driver; PageFactory.initElements(driver, this); }`
- Holds `protected WebDriver driver` and a `protected WebDriverWait wait` (constructed with a config-driven timeout)
- Provides shared helpers used by all Page Objects: `waitForVisibility(WebElement)`, `waitForClickable(WebElement)`, `isDisplayed(WebElement)`, `scrollIntoView(WebElement)`, `switchToNewWindow()`

### `DriverFactory.java` / `DriverManager.java`

- `DriverFactory` creates a browser instance per `BrowserType` (`CHROME`, `FIREFOX`, `EDGE`, `SAFARI`) using WebDriverManager for binary setup and headless/remote (Selenium Grid) options driven by config
- `DriverManager` wraps the created driver in a `ThreadLocal<WebDriver>` and exposes `getDriver()`/`setDriver()`/`quitDriver()`

## Page Object Model Conventions

- One Page Object class per application module/area: `<Module>Page.java` in package `pages.<area>.<module>`
- Class extends `BasePage`; constructor `public <Module>Page(WebDriver driver) { super(driver); }`
- Locators declared as `private WebElement`/`private List<WebElement>` fields annotated `@FindBy(...)` — **never** inline `driver.findElement(By...)` calls scattered through action methods
- Follow `03-standards/locator-standards.md` priority order, mapped to Selenium's `@FindBy` attributes:
  - `@FindBy(id = "...")` when a stable `id` exists
  - `@FindBy(css = "[data-testid='...']")` for `data-testid` hooks (preferred when no stable `id`)
  - `@FindBy(xpath = "//*[@role='button' and normalize-space()='...']")` only as a last resort, or when semantic role-based location is otherwise unavailable
- Section banners in order, as comments: `// ==== Locators ====` → `// ==== Validations ====` (if the page exposes state-check methods) → `// ==== Page Actions ====`
- Action methods use fluent chaining (`return this;`) when composed together in test flows; validation methods return `boolean`
- Every interaction goes through an explicit wait (`WaitUtils.waitForClickable(driver, element).click();`) — never a raw `element.click()` with no preceding wait, and never `Thread.sleep()`
- Page Objects are instantiated directly in test classes (`new <Module>Page(driver)`) or via a lightweight `PageFactory`/`PageManager` helper class if the target project already uses one — do not introduce a Playwright-style `ILocator`/fluent-getter wrapper; Selenium's own `@FindBy` + `PageFactory.initElements()` is the idiomatic mechanism

## Live DOM Verification

See `03-standards/locator-standards.md`'s "Live DOM Verification" section for the full rationale and cross-stack process — this section covers only this stack's mechanics.

Before writing a module's Page Object for the first time, run a throwaway `main()` (a one-off class, e.g. `DomSnapshotTool.java`, deleted after use — not part of the generated framework) that launches a real WebDriver session via `WebDriverManager`, navigates to the module's screen (performing any required setup, e.g. login), and collects the real DOM via `JavascriptExecutor` instead of trusting the documented locator table:

```java
String script =
    "const selectors = ['button','a','input','select','textarea','[role]','[data-testid]','label'];" +
    "return Array.from(document.querySelectorAll(selectors.join(','))).slice(0,150).map(el => ({" +
    "  tag: el.tagName.toLowerCase(), id: el.id||'', className: el.className||'', name: el.getAttribute('name')||''," +
    "  role: el.getAttribute('role')||'', dataTestId: el.getAttribute('data-testid')||''," +
    "  placeholder: el.getAttribute('placeholder')||''," +
    "  text: (el.textContent||'').trim().replace(/\\s+/g,' ')" +
    "}));";
List<Map<String, Object>> snapshot = (List<Map<String, Object>>) ((JavascriptExecutor) driver).executeScript(script);
new ObjectMapper().writeValue(new File("docs/dom-snapshots/<module>.json"), snapshot);
```

Cross-check every locator you're about to declare via `@FindBy(...)` against this snapshot before writing it — not after the fact. Keep the generated `docs/dom-snapshots/<module>.json` (relative to the project root) for traceability, and note any documented-vs-actual discrepancy directly in the generation summary.

## TestNG Test Class Conventions

- One TestNG test class per module: `<Module>Test.java` in package `tests.<module>`, extends `BaseTest`
- One `@Test` method per test case; method name expresses the scenario (`loginWithValidCredentials`, `loginWithInvalidPassword_shouldShowError`)
- Reference the TC ID in a `//` comment directly above the method
- Tag every test via `@Test(groups = {"smoke"})` / `@Test(groups = {"regression"})` (add project-specific groups the same way, e.g. `"sanity"`)
- Data-driven tests use a TestNG `@DataProvider` method (backed by `CSVLoader`/`JsonLoader`) referenced via `@Test(dataProvider = "...")`
- Assertions via `AssertionUtil` (wrapping TestNG `Assert`/`SoftAssert`), ending soft-assert sequences with `assertAll()`/`softAssert.assertAll()`
- Log key checkpoints via `ExtentReportManager.info/pass/fail(...)`
- Test cases with Automation Candidate = `NO` or `TBD` are skipped entirely — do not generate a stub test method for them. A `TBD` case must be re-evaluated and re-classified `YES` before automation (never delete or silently skip a `YES` test case).

## TestNG Suite XML Conventions

- `config/testng_config.xml` (or `testng.xml` at the project root, matching detected convention) defines one `<test name="<Module> Tests">` block per module, referencing its `<class name="...tests.<module>.<Module>Test"/>`
- Group-based inclusion via `<groups><run><include name="smoke"/></run></groups>` for smoke-only suite runs, and a separate `<test>`/suite file (or `<include name="regression"/>`) for regression runs
- `parallel="methods"` or `parallel="classes"` with `thread-count` set only when the framework's `DriverManager` uses `ThreadLocal<WebDriver>` (mandatory for this framework — see Base Classes)

## Waiting Strategy

- **Never** use `Thread.sleep()` under any circumstance.
- Always use `WebDriverWait` + `ExpectedConditions` (e.g., `wait.until(ExpectedConditions.elementToBeClickable(element))`) or Selenium 4's `FluentWait` for polling with custom exception ignores.
- Do not rely on a global implicit wait combined with explicit waits (mixing the two causes unpredictable timeouts) — configure `driver.manage().timeouts().implicitlyWait(Duration.ZERO)` and use explicit waits exclusively.
- Centralize wait logic in `WaitUtils` so Page Objects never construct a raw `new WebDriverWait(...)` inline.

## Reporting & Logging

- ExtentReports: initialize once per suite run (`@BeforeSuite`), attach failure screenshots via `ExtentTest.fail(..., MediaEntityBuilder.createScreenCaptureFromPath(...))`
- Log4j2: use a named logger per class (`private static final Logger log = LogManager.getLogger(<Class>.class);`), never `System.out.println` in production code paths
- Screenshot capture on failure via `ScreenshotUtils.capture(driver, testName)`, saved under `test-output/screenshots/`

---

## Constraints

- Never introduce Playwright (`com.microsoft.playwright:playwright`) or Cypress dependencies into a Selenium project, and never mix Selenium and Playwright Page Objects/tests within the same generation run or target project.
- Never use JUnit as the test runner for new artifacts in this framework — TestNG only, unless the target project's Framework Profile shows an existing, already-active JUnit setup, in which case flag the mismatch and confirm with the user before generating.
- Never hardcode credentials, URLs, or environment values — read from `config-<env>.properties`/`ConfigurationManager` or CSV/JSON test data.
- Never commit browser driver binaries — WebDriverManager only.
- Never use `Thread.sleep()` — explicit waits only.
- Never instantiate `WebDriver` as a static, non-thread-local field.
