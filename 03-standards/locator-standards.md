# Locator Standards

## Objective

Establish a consistent, stable, and maintainable locator strategy for all UI automation scripts generated by this QA-AI-Framework.

These standards apply to Playwright, Selenium, Cypress, WebdriverIO, and Appium (mobile) automation.

---

## Live DOM Verification (Mandatory for First-Time Generation)

**Documentation is a starting point, never the source of truth for a locator.** Requirement documents, PRDs, and even a dedicated "locator table" in `RequirementAnalysis.md` can be stale, incomplete, or simply wrong — this framework has repeatedly found real, live-application discrepancies from documented values (a class attribute with an undocumented trailing space, an error message missing its actual prefix, an attribute that doesn't exist at all). Relying on documentation alone means these gaps surface as flaky/failing tests *after* generation, discovered by accident during debugging, instead of being caught *before* a single locator is written.

**The rule: the first time a module is automated, every locator written into its Page Object must be confirmed against a real, live snapshot of the target application's UI — not transcribed from a document on trust.** This applies across all five supported UI stacks (Playwright, Selenium, Cypress, WebdriverIO, Appium) and is a mandatory step in Phase 2 (Page Object generation) of every automation orchestrator, not an optional nice-to-have. For the four web stacks the snapshot is a browser DOM query; for Appium (mobile) there is no DOM — the equivalent artifact is the native UI element hierarchy returned by `driver.getPageSource()` (an XML tree of `resource-id`/`content-desc`/`class`/`text` on Android, `name`/`label`/`type`/`value` on iOS). Same discipline, different snapshot mechanism — see `03-standards/appium-java-standards.md`'s "Live UI Hierarchy Verification" section for mobile's exact mechanics.

### Process

0. **Confirm prerequisites before launching anything.** Two or three things are **not** guaranteed to be available, and must never be assumed:
   - **The base URL (web) is normally already available** — every automation agent already consumes `RequirementAnalysis.md`'s documented "Environment URLs" as a standard input, so reuse that rather than asking again. **Per-page paths** may also be documented (a URL map, e.g. `RequirementAnalysis.md §12`), letting the target screen be reached directly; without one, the tool must reach it by actually driving the UI instead of guessing a path.
   - **The app binary path or installed-app identifier (mobile).** Appium cannot start a session at all without either an APK/IPA file path or, for an already-installed app, `appPackage`+`appActivity` (Android) / `bundleId` (iOS). Unlike a web base URL, this is almost never present in a PRD/requirements document by default — check `RequirementAnalysis.md` and the project brief for it explicitly, and **if it isn't found anywhere, stop and ask the user before attempting to scaffold or verify anything** — there is no way to proceed, guess, or default a mobile app's binary location.
   - **Credentials for any module gated behind login/auth** (web or mobile). Check `RequirementAnalysis.md` and `FunctionalTestCases.md`'s test data for already-documented, explicitly-test credentials (as SauceDemo's PRD happened to provide) — do not assume every project's source documents will include these; most real client PRDs deliberately omit credentials from requirements docs. **If credentials for a gated module are not found anywhere in the already-loaded inputs, stop and ask the user for them explicitly before attempting to reach that module.** Never invent, guess, or reuse credentials from an unrelated context, and never silently skip verification for a gated module without saying so — a skipped verification is a gap, not a non-event.
   - Modules with no auth requirement (typically the login/auth module itself, or a mobile app's initial launch screen) have no such dependency and can proceed directly.
1. **Before writing any Page Object for a module**, launch a real (typically headless, or a real emulator/simulator for mobile) session against the application, and navigate to the specific screen the module covers — performing whatever setup flow is required to reach it (e.g., logging in first, using credentials confirmed in step 0 and the already-verified locators from the login/auth module itself — verify modules in dependency order, auth first, so every later module's setup flow has real, working locators to drive through rather than guessing at unverified ones).
2. **Take a UI snapshot** of the screen. Web: query `button, a, input, select, textarea, [role], [data-testid], label` and capture each element's `id`, `class`, `name`, `role`, `aria-label`, `data-testid`, `placeholder`, `for`, and visible text — the same candidate shape the self-healing mechanism collects at runtime (see each stack standard's "Self-Healing Locators" section), because it is solving the same underlying problem: "what does this element actually look like right now?" Mobile: call `driver.getPageSource()` and parse the returned XML for the same kind of candidate attributes (see `03-standards/appium-java-standards.md`'s mechanics section).
3. **For every locator about to be written into the Page Object:**
   - If the documented value (from `RequirementAnalysis.md`, a test case, or a Figma spec) matches a real element in the snapshot exactly — use it. No discrepancy to report.
   - If it does **not** match anything in the snapshot — do not transcribe it anyway. Find the actual best-matching element in the snapshot (following the Priority Order below), use its **real** value, and record a discrepancy note: module, the documented value, the actual value, and the date the snapshot was taken. This is a `GapAnalysis.md`-style finding, not a silent substitution — surface it, don't bury it.
   - If nothing plausible exists in the snapshot at all — stop and flag it as a blocking gap for that specific element. Do not guess a locator for an element you cannot confirm exists.
4. **Persist the snapshot** for traceability — see each stack standard's "Live DOM Verification" section for the exact file location convention. A reviewer should be able to see what was actually confirmed, and when, without re-running the browser themselves.
5. This runs **once per module** during initial Page Object generation, not once per locator in isolation and not repeated on every subsequent run — a module that already has a Page Object and is only gaining new scenarios does not need to re-verify locators it already confirmed, unless the target application's URL/version has materially changed.

### Relationship to self-healing

Live DOM verification and self-healing solve the same problem at two different times: verification catches a documentation/reality mismatch **before** it ships as a broken locator; self-healing catches a locator that **was** correct and has since drifted, at runtime. Neither replaces the other — a module with well-verified initial locators still benefits from self-healing against future drift, and self-healing does not excuse skipping verification at generation time (a healed-on-every-run locator that was never actually confirmed correct is a silent, permanent crutch, not a substitute for getting it right initially).

## Locator Priority Order

Always select locators using this priority order:

| Priority | Strategy | When to Use |
|---|---|---|
| **1** | `data-testid` attribute | Preferred: developer-assigned stable test hooks |
| **2** | ARIA Role + Accessible Name | Buttons, links, headings, inputs with roles |
| **3** | Label text | Form inputs with `<label>` elements |
| **4** | Placeholder text | Input fields without visible labels |
| **5** | Visible text | Buttons, links, headings with stable text |
| **6** | `id` attribute | Only when `id` is stable and not auto-generated |
| **7** | CSS selector (stable) | When above options are unavailable |
| **8** | XPath | Last resort only |

## Playwright Locator Examples

```typescript
// Priority 1 — data-testid (most stable)
page.getByTestId('submit-button')
page.getByTestId('email-input')

// Priority 2 — ARIA role
page.getByRole('button', { name: 'Add to Cart' })
page.getByRole('link', { name: 'Checkout' })
page.getByRole('heading', { name: 'Order Confirmation' })
page.getByRole('textbox', { name: 'Email Address' })

// Priority 3 — Label
page.getByLabel('Password')
page.getByLabel('Mobile Number')

// Priority 4 — Placeholder
page.getByPlaceholder('Enter your email')

// Priority 5 — Visible text
page.getByText('Proceed to Checkout')

// Priority 6 — ID (stable only)
page.locator('#login-form')
page.locator('#product-title')

// Priority 7 — CSS (stable, semantic)
page.locator('.product-card .product-title')
page.locator('[data-module="checkout"]')

// Priority 8 — XPath (last resort)
page.locator('//button[contains(@class,"submit") and text()="Login"]')
```

## Locator Anti-Patterns (Forbidden)

Never use:

```typescript
// Auto-generated class names
page.locator('.css-1a2b3c')               // ❌ Generated by CSS-in-JS

// Index-based without stable parent
page.locator('button').nth(0)             // ❌ Fragile — order can change

// Deep layout-dependent XPath
page.locator('//div[3]/table/tbody/tr[2]/td[1]/a')  // ❌ Breaks on layout change

// Text combined with layout index
page.locator('div:nth-child(5) span')     // ❌ Position-dependent

// Hardcoded style attributes
page.locator('[style="color: red"]')      // ❌ Style changes break this
```

## Locator Declaration Rules

Two conventions are supported depending on the target framework:

**Cucumber + Playwright (BDD) projects — default for this QA-AI-Framework:** Declare locators as **getter methods** returning `Locator`, directly on the page class (see `03-standards/playwright-typescript-standards.md`). Do not use a shared `LocatorRepo`.

```typescript
// GOOD — getter, evaluated fresh on each access
get loginButton(): Locator {
  return this.page.getByRole('button', { name: 'Login' });
}
```

**Plain `@playwright/test` runner projects (only if explicitly requested):** Declare all locators in the Page Object constructor as `private readonly` fields.

```typescript
// GOOD — declared in constructor
private readonly loginButton: Locator;
constructor(page: Page) {
  this.loginButton = page.getByRole('button', { name: 'Login' });
}
```

In both conventions:
- Never declare or construct locators inline inside action methods or test/step files.
- Use descriptive camelCase names: `loginButton`, `emailInputField`, `errorMessageText`.

```typescript
// BAD — inline in method
async clickLogin() {
  await this.page.getByRole('button', { name: 'Login' }).click(); // ❌
}
```

## Dynamic Locator Patterns

When locators contain dynamic values (e.g., product IDs, user-specific text):

```typescript
// Parameterized locator — use a method
getProductCard(productName: string): Locator {
  return this.page.getByTestId(`product-card-${productName}`);
}

getOrderRow(orderId: string): Locator {
  return this.page.locator(`[data-order-id="${orderId}"]`);
}
```

## Locator Naming Conventions

| Element Type | Suffix | Example |
|---|---|---|
| Button | `Button` | `addToCartButton` |
| Input field | `Input` | `emailInput` |
| Dropdown | `Dropdown` | `countryDropdown` |
| Checkbox | `Checkbox` | `termsCheckbox` |
| Radio button | `Radio` | `paymentMethodRadio` |
| Link | `Link` | `forgotPasswordLink` |
| Text / Label | `Text` | `welcomeMessageText` |
| Error message | `Error` | `loginError` |
| Container / Section | `Section` | `cartSummarySection` |
| Modal / Dialog | `Modal` | `confirmationModal` |
| Table row | `Row` | `orderTableRow` |

## Locator Scoping

Always scope child locators to their parent when elements are repeated on the page:

```typescript
// GOOD — scoped to specific cart item
const cartItem = page.getByTestId('cart-item').filter({ hasText: 'Headphones' });
await cartItem.getByTestId('remove-button').click();

// BAD — ambiguous when multiple remove buttons exist
await page.getByTestId('remove-button').click(); // ❌ may interact with wrong item
```

## data-testid Convention

Recommend the following `data-testid` naming convention to development teams:

Format: `<component>-<element>-<action-or-type>`

Examples:

```html
<input data-testid="login-email-input" />
<input data-testid="login-password-input" />
<button data-testid="login-submit-button">Login</button>
<span data-testid="login-error-message">Invalid credentials</span>
<div data-testid="cart-item" data-product-id="123">...</div>
<button data-testid="cart-remove-button">Remove</button>
```

## Locator Review Checklist

Before committing:

- [ ] All locators use Priority 1–5 where possible
- [ ] No auto-generated class names used
- [ ] No index-based locators without stable parents
- [ ] All locators declared in Page Object constructor
- [ ] Dynamic values handled via parameterized methods
- [ ] Locator names follow naming convention
- [ ] Child locators scoped to parent when elements repeat
- [ ] XPath used only when no other strategy is viable (documented with reason)
