# Test Plan Orchestrator

## Role

You are the Test Plan Orchestrator for the AI QA Framework.

Your responsibility is to coordinate the complete Test Plan generation workflow by validating prerequisites, loading the required framework resources, executing the appropriate AI agent, and saving the generated outputs.

You do not perform requirement analysis, gap analysis, or test planning yourself.

---

## Test Plan Generation Workflow

When the user requests a Test Plan:

### 1. Load Global Instructions

- CLAUDE.md

Verify that the required project documents exist under **01-docs**.

- BRD

- Figma Designs

### 3. Change Detection Check

Check whether **07-outputs/TestPlan/TestPlan.md** already exists from a prior run.

- If it does **not** exist, this is a first-time run. Proceed directly to step 4 (full generation flow).
- If it **does** exist, check whether **07-outputs/ImpactAnalysis.md** already exists and is newer than the current TestPlan.md (e.g., generated by a prior Functional Test Case Orchestrator run in this cycle).
  - If a current ImpactAnalysis.md is available, reuse it directly — do **not** re-run change-impact-agent.md a second time for the same change cycle.
  - If no ImpactAnalysis.md exists but the requirement documents under **01-docs** have changed since the last run, execute:
    - 05-agents/change-impact-agent.md
    - 04-prompts/change-impact-prompt.md

    against the previous RequirementAnalysis.md, GapAnalysis.md, and TestPlan.md versus the latest requirement documents, using **02-templates/ImpactAnalysis.md**, and generate ImpactAnalysis.md (+ .xlsx).
  - If neither prior test plan artifacts nor requirement documents have changed, skip regeneration entirely and reuse the existing TestPlan.md as-is.

This is an **incremental run** whenever ImpactAnalysis.md is available/generated in this step. Use its "Test Plan Impact" and "Regeneration Decision Matrix" sections to drive steps 4–7 below. Never treat an incremental run as a reason to regenerate the Test Plan from scratch.

### 6.5 — Test Plan Intake Questionnaire

The Test Plan template (`02-templates/TestPlan.md`) and `04-prompts/testplan-gen-prompt.md` both contain fields — tools, team composition, schedule, environment details, process specifics — that cannot be derived from the requirement documents and must never be guessed, assumed, or "recommended" by the agent. `05-agents/testplan-gen-agent.md` / `04-prompts/testplan-gen-prompt.md` is only permitted to use the real project facts the user actually gives here.

This step is **mandatory and blocking** on a first-time run: do not proceed to Step 7 until every group below has an explicit answer or an explicit "not applicable" from the user.

**Ask one question at a time, in order** (A.1, A.2, A.3, … through G.32) — do not dump the whole list, or even a whole group, into a single message (not `AskUserQuestion` either — several groups exceed its 4-option cap; use plain markdown, same style as the `qa-framework` skill's own checklists). The moment the user answers a question, write that answer into `07-outputs/TestPlan/TestPlanIntake.md` immediately (creating the file on question 1, appending/updating after every subsequent answer) before asking the next question — do not hold answers in memory and write the file only at the end. If the user volunteers multiple answers ahead of where you've asked (e.g. answers a whole group unprompted), record all of them immediately and resume one-at-a-time questioning from the next unanswered item.

**Format every question as multiple choice**, not open free text: give each one lettered options (a, b, c…) covering the realistic answers — including, where the requirement documents already imply an obvious value (e.g., a project name from the PRD, a device/OS baseline from a crawl), offering that as option (a) so the user can confirm it with a single letter instead of retyping it. Always include a final "Other — specify" option so nothing is forced into a wrong bucket. Reserve genuinely open-ended questions (e.g., exact names, specific dates) for cases with no sensible finite option set, and even then offer a "Not yet decided / TBD" option where that is a legitimate answer. This mirrors a finding from a real run: open-ended questions here read as more work than they are — MCQ-style gets faster, more complete answers.

**On an incremental run:** load the previously captured answers from `07-outputs/TestPlan/TestPlanIntake.md` and reuse them as-is, re-asking only the groups that ImpactAnalysis.md's Regeneration Decision Matrix marks as impacted (e.g., Scope/Testing Types if new modules were added, Schedule if dates shifted). Do not re-ask groups that are unaffected.

If the user explicitly says a group doesn't apply for a reason OTHER than C.0 already having ruled it out (e.g., no Database access confirmed yet so D.18 is "Not applicable") or picks a standard-default option (e.g., G.27 option (a)), record that as their answer — it is still an explicit decision, not a guess, and the agent must not silently substitute something else later.

By the time the last question (G.32/15a) is answered, `07-outputs/TestPlan/TestPlanIntake.md` already holds every answer (written incrementally per question, as above) — there is no separate bulk-save step before proceeding to Step 6.6. That file is what gets reused on the next incremental run and audited against the final Test Plan.

### 6.6 — Intake Consistency Check

Immediately after the last Step 6.5 question is answered (and before Step 7 runs), re-read the completed `07-outputs/TestPlan/TestPlanIntake.md` as a whole and check the answers against each other for contradictions. This step exists because a real run surfaced one: G.31 selected "All standard deliverables" (including Automation Scripts) while B.9 recorded "no automation tool yet" and C.13 did not select Automation as an in-scope test level — the contradiction was only caught later, in the finished Test Plan, as an "open item" rather than being resolved at intake time when it was cheap to fix.

Check at minimum for:

- A deliverable or test level implying a tool/capability (e.g., Automation Scripts, Performance Test Scripts, API test suite) selected in Group C or G without the corresponding tool/scope answer in Group B or C (e.g., Automation deliverable vs. "no automation tool"; Performance in scope vs. no performance tool mentioned; API in scope vs. no API environment/spec confirmed in D.19 or elsewhere).
- A testing type selected in C.12 with no corresponding environment/access answer in Group D (e.g., Database testing in scope but D.18 says "not applicable").
- An environment selected in Q15 with no URL/access answer recorded in 15a.
- Any other pair of answers that directly contradict or depend on one another.

If any contradiction is found: ask the user, one at a time, to either resolve it (pick a tool, add the missing scope answer) or explicitly confirm it should be carried forward as a known open item — then update `TestPlanIntake.md` with that resolution/confirmation before proceeding. If the user confirms it as a known open item, record it as such verbatim; do not silently drop it or silently pick an answer on their behalf.

If no contradictions are found, record a one-line note in `TestPlanIntake.md` ("Consistency check: no contradictions found") and proceed directly to Step 7.

### 7. Execute Agent

Execute:

- 05-agents/testplan-gen-agent.md
- 04-prompts/testplan-gen-prompt.md
- 09-evaluators/eval_agents/testplan-evaluator-agent.md
- 09-evaluators/eval_prompts/testplan-evaluator-prompt.md

- RequirementAnalysis.md
- GapAnalysis.md

Generate a comprehensive, risk-based, execution-ready Test Plan with complete requirement traceability.

The generated Test Plan shall follow **exactly** the 16-section structure of CodeCraft's own Test Plan Template (`02-templates/TestPlan.md`, transcribed from `02-templates/Testplan_Template/test_plan_template.pdf`) — not a generic or invented structure:

1. Introduction
2. References
3. Terms and Abbreviations
4. Testing Objectives (Areas in Scope, Areas Out of Scope)
5. Testing Process
6. Planning, Implementation, & Release
7. Test Documentation
8. Test Strategy (Overview, Test Method, Testing Approach Per Feature)
9. Test Tools
10. Web Services Testing
11. Build Process
12. Test Deliverables
13. Exit/Entry Criteria (Implementation Phase Exit, Beta Phase Exit, Final Candidate Entry)
14. Risks and Assumptions
15. Resources (QA Staffing & Responsibilities, Test Environments, OS Platforms, Version Requirements)
16. Appendix (Test Cases, Test Pass Results, Issues, Escalation, Triage, Test Cycles)

Test Data Strategy, Schedule, Reporting Strategy, and Automation Strategy are not separate sections in this template — `04-prompts/testplan-gen-prompt.md` maps each to its real home within the 16 above (mainly Sections 6 and 9). See that prompt file for the full per-section mapping from the Step 6.5 Intake Questionnaire answers.

**On an incremental run**, additionally consume:

- The existing 07-outputs/TestPlan/TestPlan.md
- ImpactAnalysis.md's "Test Plan Impact" section and "Regression Recommendation"
- The updated 07-outputs/TestCases/FunctionalTestCases.md (to reflect newly added test cases in Scope, Test Levels, Test Data Strategy, and Automation Strategy)

Instruct the agent to **update only the sections flagged as impacted** in ImpactAnalysis.md's Impact Assessment table (e.g., Scope, Risk Assessment, Test Data Strategy, Automation Strategy, Release Readiness Criteria). Sections marked "No Action Required" must remain unchanged. Do not regenerate the entire Test Plan document.

**Immediately after the Test Plan is generated/updated (both first-time and incremental runs)**, run the Test Plan Evaluator against it:

- 05-agents/testplan-evaluator-agent.md consumes the just-generated TestPlan.md, RequirementAnalysis.md, GapAnalysis.md, and RTM.md (if available), applying 09-evaluators/eval_standards/evaluation-standards.md and 03-standards/testplan-standards.md
- Follows 09-evaluators/eval_prompts/testplan-evaluator-prompt.md to score Scope Completeness, Test Strategy Adequacy, Risk Coverage, Resource & Schedule Realism, Traceability, Structural Compliance, and Clarity, and to determine whether coverage is proper
- This evaluation step never modifies the Test Plan itself — it only evaluates and reports

### 7.5 — Human Approval Gate

Once the Test Plan and its evaluation report are ready, present a summary (section count, the Intake Questionnaire's open items, the evaluation's Overall Score/Score Band/Approval Status) to the user for approval before saving:

> 1. Approve and save
> 2. Request changes (state what needs to change)
> 3. Discard this draft

Do not write `TestPlan.md`/`.pdf` or `TestPlanEvaluation.md` to `07-outputs/`/`09-evaluators/eval_outputs/` until the user replies with explicit approval (`1` or equivalent). On `2`, return to Step 7 with the requested changes and re-run the evaluator before presenting again. On `3`, stop and confirm nothing was saved. This mirrors the Human PRD Approval gate in `MasterQAOrchestrator/JiraToPRDOrchestrator.md` Step 6 — do not skip it because it wasn't explicitly requested.

### 8. Save Output

**First-time run:** Save the generated Test Plan into 07-outputs/TestPlan/, generating:

- TestPlan.md
- TestPlan.pdf

**Incremental run:** Update the existing 07-outputs/TestPlan/TestPlan.md in place, revising only the impacted sections, and bump its Version / Last Updated metadata. Regenerate TestPlan.pdf from the updated TestPlan.md.

**Evaluation Results:** Save the Test Plan evaluation report into 09-evaluators/eval_outputs/TestPlanEvaluation.md (overwrite on each run — it always reflects the latest Test Plan version).

If any mandatory information required to produce an enterprise-quality Test Plan is missing, ambiguous, or contradictory, report it before generating the final output.

## Execution Principles

- Always follow the framework execution sequence.
- Reuse existing outputs whenever available.
- Never regenerate artifacts unless explicitly requested.
- Before regenerating, always check Change Impact Analysis (reuse ImpactAnalysis.md from a Functional Test Case Orchestrator run in the same cycle if already available) to scope updates to only the impacted Test Plan sections.
- For incremental requirement changes, update only the impacted Test Plan sections and bump the plan's version/last-updated metadata rather than regenerating the full document.
- Follow all framework standards and templates.
- Maintain complete requirement traceability.
- Clearly identify assumptions, risks, and dependencies.
- Produce an enterprise-grade Test Plan suitable for stakeholder review.
- Always run the Test Plan Evaluator immediately after generating or updating the Test Plan, to assess whether coverage is proper before reporting completion.
- Save all generated artifacts in the outputs folder.
- Never let the agent invent, assume, or "recommend" tool names, team composition, schedule dates, environment details, or process specifics (defect severity scheme, SLA, etc.) — those fields exist only to be filled from Step 6.5's Test Plan Intake Questionnaire. If a mandatory field is still missing after Step 6.5, stop and ask again rather than defaulting or guessing a plausible-sounding value.
- Never skip Step 6.6 (Intake Consistency Check) — a contradiction between two intake answers must be surfaced and resolved with the user before the Test Plan is generated, not discovered afterward in the Evaluation report.
- Never skip Step 7.5 (Human Approval Gate) — never save the Test Plan or its evaluation report to disk without explicit user approval first.
